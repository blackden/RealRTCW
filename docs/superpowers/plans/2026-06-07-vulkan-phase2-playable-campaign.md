# RealRTCW Vulkan Phase 2 — Playable Campaign on MoltenVK

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the vendored Quake3e `renderervk` up on RealRTCW + MoltenVK on Apple Silicon to the point that the Wolfenstein single-player campaign is playable end-to-end (boot menu → load → play first level → no validation errors, no rendering regressions vs. the OpenGL renderer).

**Architecture:** RealRTCW already uses Q3-style renderer dlopen (`USE_RENDERER_DLOPEN=1`) — the engine talks to a renderer DLL via two vtables, `refImport_t` (engine→renderer) and `refExport_t` (renderer→engine), declared in `code/renderer/tr_public.h` and `code/renderer/tr_types.h`. The checkpoint `95177e7` on `macos-arm64-vulkan` vendored Quake3e's `renderervk/` and `renderercommon/` and started wiring the Makefile, but the Quake3e ABI has drifted from RealRTCW's (new `cvarValidator_t`, extra `refdef_t` fields, different `refEntity_t` layout, `NORETURN_PTR`/`FORMAT_PRINTF` macros). We solve drift with a **shim header layer** (`code/renderervk/realrtcw_shims.h`) included before vendored sources, mapping new identifiers onto RealRTCW equivalents and providing stubs where semantics genuinely differ. Once linking works, iterate via `vk-validation-triage` → fix loop, then `mvk-frame-capture` for any remaining visual bugs.

**Tech Stack:** C99, GNU Make, LunarG Vulkan SDK 1.4.350.0 (`~/VulkanSDK/1.4.350.0`), MoltenVK (shipped with SDK), glslangValidator (SPIR-V compile), Apple Silicon Metal backend.

**Branch:** `macos-arm64-vulkan` (current tip `95177e7`). All work commits there. Push only after each milestone, with ragnar's OK (see memory: `feedback-push-gating`).

**Toolkit references:** `~/.claude/q3-port-toolkit-README.md` overview. Skills used along the way: `q3-renderer-abi-diff`, `vk-validation-triage`, `mvk-frame-capture`, `q3-engine-archaeology`, `mac-game-port-toolkit`. Agents: `q3-fork-detective` (one-symbol cross-fork lookups), `vulkan-validation-analyst` (validation log triage). Vendor-guard hook `.claude/hooks/block-vendored-renderervk.sh` is active — escape hatch is `REALRTCW_ALLOW_VENDOR_EDIT=1 claude` only for genuine re-vendor work.

**Out of scope for this plan:** OpenGL renderer regressions, Windows/Linux Vulkan paths, MetalFX upscaling, Metal-native renderer (separate xrRenderMetal project lives in the xray-16 fork), shader hot-reload, validation-layer-clean profiling.

## Milestone 2 — Shim Layer + Vtable Adapter + Engine Glue (Build Reaches Link)

End state: `make ARCH=arm64 BUILD_RENDERER_VULKAN=1` compiles every renderervk and renderercommon `.c` without errors. Link step may still fail — that's Milestone 3 territory.

**Scope expanded after M1.3 discovery (a86b6c5):** Quake3e renderervk is **self-contained** — it carries its own `refimport_t`/`refexport_t` definitions in `code/renderervk/tr_local.h`, NOT shared with RealRTCW's `code/renderer/tr_public.h`. So M2 now includes a full vtable adapter (Task 2.4), not just per-identifier shims. Per-identifier macro/typedef/function shims (Tasks 2.1-2.3) handle compile-time symbol resolution; the vtable adapter (2.4) handles runtime engine↔renderer protocol divergence; high-risk engine-side items (2.5) handle the struct-field rename + renderercommon header privacy issues that can't be shimmed.

**Code-craft notes** accepted as PROCEED-WITH-NOTES (see plan revision commit message):
- Principle 1 (single source of truth): `refEntity_t.shader` has dual representation — engine-side `byte shaderRGBA[4]`, vendored-side `color4ub_t shader` union. Accepted: `realrtcw_engine_glue.c` is the SOLE conversion site; any engine-side edit of the field must synchronize there. Alternative (engine adopts union) explodes scope.
- Principle 5 (layering): `realrtcw_engine_glue.c` bridges engine internals and Quake3e renderervk structs. Accepted: unavoidable while vendoring approach holds. Mitigation: glue exposes a single entry point (`RealRTCW_BuildQuake3eRefImport()`) to engine; engine never sees Quake3e structs directly.

Drift catalog driving M2: `docs/vulkan-phase2-abi-diff.md` (commit `a86b6c5` on `macos-arm64-vulkan`). 18 root items, 23 summary-table entries.

- [ ] **Step 1: Prefer `static inline` in shim header where possible**

Example inline pattern:

```c
/* log2pad: ceil-power-of-2 log2. Quake3e qcommon.h has this as static
 * ID_INLINE. RealRTCW does not. Define inline in shim header so every
 * renderervk source picking up the -include gets the symbol. */
static inline unsigned int log2pad(unsigned int v, int roundup)
{
    unsigned int r = 0;
    if (roundup && v && (v & (v - 1))) v <<= 1;
    while ((v >>= 1) != 0) r++;
    return r;
}
```

Example wrapper pattern in glue file:

```c
/* Com_GenerateHashValue: Quake3e wants this exposed; RealRTCW has
 * static `generateHashValue` in tr_shader.c. Re-implement here with
 * identical FNV-1a hash semantics so callers get the same hash result. */
int Com_GenerateHashValue(const char *fname, const int size)
{
    int hash = 0;
    for (int i = 0; fname[i]; i++) {
        char letter = tolower((unsigned char)fname[i]);
        if (letter == '\\') letter = '/';
        hash += (int)(letter) * (i + 119);
    }
    return hash & (size - 1);
}
```

### Task 2.4: Quake3e-style refImport_t vtable adapter

**Goal:** Quake3e renderervk expects a `refimport_t` vtable defined in `code/renderervk/tr_local.h` that differs from RealRTCW's `refImport_t` in `code/renderer/tr_public.h` (extra `Cvar_Get` validator arg, possibly new method slots). Build an adapter in `realrtcw_engine_glue.c` that constructs the Quake3e-style vtable from RealRTCW's existing engine functions and hands it to renderervk at startup.

**Architectural constraint (from code-craft check):** Engine never sees Quake3e structs. Glue exposes ONE entry point: `void RealRTCW_BuildQuake3eRefImport(void *out_q3e_ri);` — engine passes opaque buffer, glue fills it. Header `code/renderervk/realrtcw_engine_glue.h` declares only this entry point.

**Files:**
- Create: `code/renderervk/realrtcw_engine_glue.h` (single function declaration)
- Modify: `code/renderervk/realrtcw_engine_glue.c` (add adapter implementation)
- Modify: engine-side init site where `ri.*` is populated for renderer (find via `grep -n "ri.Cvar_Get\s*=" code/client/cl_main.c code/server/sv_init.c` and adjacents) — replace direct RealRTCW `refImport_t` population for Vulkan renderer with `RealRTCW_BuildQuake3eRefImport(&ri)`.

- [ ] **Step 1: Catalog Quake3e refimport_t field-by-field**

Read `code/renderervk/tr_local.h` in the worktree. Find the `refimport_t` (lowercase per Quake3e style) struct definition. List every field. For each field, look up the equivalent in RealRTCW's `code/renderer/tr_public.h` `refImport_t`. Three categories:
- **Identical signature** — direct assignment (e.g. `q3e_ri.Hunk_AllocateTempMemory = ri.Hunk_AllocateTempMemory`)
- **Trivial signature diff** — wrapper in glue (e.g. `Cvar_Get` extra `cvarValidator_t` arg → wrapper that drops it)
- **Missing in RealRTCW** — engine function that doesn't exist; needs engine-side stub OR no-op shim if renderervk only calls it conditionally

Document the catalog as a comment block at top of `realrtcw_engine_glue.c`.

- [ ] **Step 2: Write the adapter**

For each catalog row, implement the wrapper. Each wrapper is its own function, no `// similar` shortcuts. Example for `Cvar_Get`:

```c
static cvar_t *Q3eShim_Cvar_Get(const char *name, const char *value,
                                int flags, cvarValidator_t validator)
{
    (void)validator;  /* RealRTCW does not validate; drop silently. */
    return Cvar_Get(name, value, flags);
}
```

Then `RealRTCW_BuildQuake3eRefImport`:

```c
void RealRTCW_BuildQuake3eRefImport(void *out_q3e_ri)
{
    Quake3eRefImport_t *q3e = (Quake3eRefImport_t *)out_q3e_ri;
    /* Forward identical-signature methods directly. */
    q3e->Printf              = Com_Printf;
    q3e->Hunk_AllocateTempMemory = Hunk_AllocateTempMemory;
    /* ... full list per catalog ... */
    /* Trivial-diff methods via wrappers. */
    q3e->Cvar_Get            = Q3eShim_Cvar_Get;
    /* ... */
}
```

Where `Quake3eRefImport_t` is a typedef in `realrtcw_shims.h` matching the Quake3e `refimport_t` layout. Glue includes `realrtcw_shims.h` to get that type.

- [ ] **Step 3: Wire engine renderer-init to call adapter for Vulkan path**

Find where RealRTCW builds `refImport_t` for the renderer DLL (`grep -n "GetRefAPI\|R_GetCommandBuffer\|GetRenderer" code/client/cl_*.c`). For the Vulkan code path (which renderer DLL is currently selected), call `RealRTCW_BuildQuake3eRefImport` instead of the existing builder. Either:
- (a) Branch on cvar `cl_renderer == "vulkan"`, OR
- (b) Make the Vulkan renderer DLL its own dlopen path that always uses the adapter

Prefer (b) — it isolates the adapter to a single dispatch site. The existing renderer DLL machinery in RealRTCW already supports multi-renderer dlopen.

Quake3e renamed `byte shaderRGBA[4]` → `color4ub_t shader` (union of `byte rgba[4]` + `uint32_t u32`). Renderervk reads both `.rgba[]` and `.u32` at submission time. Engine continues writing `shaderRGBA[4]` as byte array.

Strategy: glue function `RealRTCW_ConvertRefEntityForVk(const refEntity_t *src, void *dst)` — dst is the Quake3e-layout `refEntity_t`, glue fills it from src and converts `shaderRGBA[4]` → `color4ub_t shader`. Called from the `re.AddRefEntityToScene` adapter step inside `RealRTCW_BuildQuake3eRefImport`'s exported wrappers (refExport side).

Implement, commit per code-craft note (principle 1 — dual representation; see plan-level note in M2 header).

```bash
git commit -m "build(vulkan): translate refEntity_t.shader between engine byte[4] and Quake3e color4ub_t

Engine keeps byte shaderRGBA[4]; glue converts to color4ub_t union on
AddRefEntityToScene calls into vendored renderervk.

Code-craft note (PROCEED-WITH-NOTES, principle 1 — single source of truth):
two representations of entity tint color exist (engine-side byte[4],
shim-side union). realrtcw_engine_glue.c is the SOLE conversion site;
any future change to refEntity_t.shaderRGBA must update RealRTCW_ConvertRefEntityForVk."
```

- [ ] **Step 2: `RE_RegisterShaderFromImage` exposure**

`code/renderercommon/tr_font.c` calls `RE_RegisterShaderFromImage` which lives in `code/renderer/tr_shader.c` (RealRTCW) without a public declaration. In Quake3e it's declared in `code/renderervk/tr_public.h` (renderer's own public header).

Strategy: add a forward declaration to `code/renderercommon/tr_public.h` (or create one) — minimal, just the function signature. Commit.

- [ ] **Step 3: `r_saveFontData` / `image_t` privacy fix in renderercommon/tr_font.c**

`renderercommon/tr_font.c` references `image_t` (private to renderer in RealRTCW) and writes `r_saveFontData`. In Quake3e, renderercommon was designed assuming access to private types because Quake3e merged renderer+renderercommon into a single compile unit.

Strategy: add an include of `code/renderer/tr_local.h` to the renderercommon compile rule's CFLAGS via `-I`, OR move the needed types/cvars to a smaller shared header. Prefer `-I` first (simpler).

Commit.
