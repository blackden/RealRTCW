# M2.4 vtable adapter — conditional include вместо полного glue

**Date:** 2026-06-08
**Phase:** Vulkan Phase 2, Milestone 2 (Task 2.4)
**Commit:** 285423a

## Context

В Phase 2 плане M2.4 описывался как «Quake3e-style refImport_t vtable adapter» — ожидался ~400 строк glue-кода в `code/renderervk/realrtcw_engine_glue.c` который бы:
1. Знал ОБЕ shape'ы refimport_t (RealRTCW engine 75-полей + Quake3e vendored 100-полей)
2. Экспонировал единственную функцию `RealRTCW_BuildVulkanRefImport(void *out)` engine'у
3. Engine видит opaque buffer, не Quake3e structs

Code-craft check (PROCEED-WITH-NOTES) предупреждал что glue.c необходимо мостит два слоя — принимаем как trade-off layering principle.

При попытке начать работу обнаружилось:
- Engine cl_main.c уже населяет `refimport_t ri;` 33 ассайнментами (`ri.X = Y`), но struct определена в `code/renderer/tr_public.h` (маленькая)
- Vendored renderervk консумит `refimport_t` определённую в `code/renderercommon/tr_public.h` (большая, `Shutdown` принимает `refShutdownCode_t` enum а не `qboolean`)
- Размеры разные — даже если ссылку правильно передать, vendored читает garbage из неинициализированных байтов

Перед стартом написания glue.c проверили: сигнатура `Shutdown` бинарно совместима (один регистр на argument), а большинство дополнительных полей идут «в конце» struct.

## Decision

**Не писать full vtable adapter.** Вместо этого — conditional include + zero-init:

`code/client/client.h:33`:
```c
#ifdef BUILD_RENDERER_VULKAN
#include "../renderercommon/tr_public.h"  /* 100-полей shape */
#else
#include "../renderer/tr_public.h"        /* 75-полей shape */
#endif
```

`code/client/cl_main.c:CL_InitRef` зерофицирует `ri` сразу после declaration:
```c
refimport_t ri;
refexport_t *ret;
...
Com_Memset(&ri, 0, sizeof(ri));
```

12 строк всего вместо ожидаемых ~400.

## Why

- **Симметричные ABI на двух сторонах.** Engine и renderervk обе компилируются под одну и ту же struct shape (renderercommon). Не нужен transform-on-the-fly.
- **Pragmatic compile-clean.** Цель M2 — «build reaches link» (см. plan). Полная vtable map'ка нужна для runtime correctness, а это M5 territory.
- **Trade-off acceptable.** Из 100 полей engine реально знает 33. Остальные 67 — NULL после zero-init. Если vendored renderervk вызовет один из 67 на startup'е, упадёт NULL-deref — **clean сигнал** на которое поле нужно подвести real функцию (или stub) в M5.
- **Inverse risk:** если бы написали полный adapter, легко могли передать NEEDS-WIRING поля сразу — без сигнала что они нужны. Сейчас runtime crash маркер «вот это надо подключить».

## Trade-off

- **OpenGL renderer path всё ещё использует маленькую `refimport_t`.** Conditional include при `BUILD_RENDERER_VULKAN=0` берёт `renderer/tr_public.h`. Это значит build-time выбор: либо OpenGL build, либо Vulkan build. **Не оба одновременно из одного бинарника.** Раньше можно было через USE_RENDERER_DLOPEN switch'нуть на runtime. Сейчас — нет.
- **Слепые 67 полей.** При первом запуске Vulkan build'а ожидаем NULL-deref в произвольном vendored callsite. Нужно будет тратить debugger-цикл на каждое. Если их много (десятки), может потребоваться откатить решение и написать full adapter.
- **`Shutdown` signature implicit conversion.** Vendored зовёт `ri.Shutdown(REF_DESTROY_WINDOW)` (= int 2), RealRTCW функция ожидает `qboolean` (enum {0,1}). Передаётся 2 — engine treats as `if (destroyWindow)` truthy, окей. **Но это implicit cast** через function pointer, который C11 ругает warning'ом. Сейчас flowgraph не падает.

## Revisit if

- **На первом playtest Vulkan build'а** ловим >5 разных NULL-deref сайтов от unpopulated slot'ов — становится дешевле написать full adapter чем фиксить по одной точке.
- **Нужен runtime switch OpenGL ↔ Vulkan** в одном бинарнике (для пользователя который хочет переключаться без rebuild'а) — придётся вернуться к идее адаптера.
- **OpenGL renderer заведомо нужен** на каком-то платформе где Vulkan недоступен — нужно build matrix с обоими.
